## 2. 확정 원칙

1. P6 연락 순서는 **B 유족 → A 유족**으로 고정한다.
2. B 유족은 범죄의 전체 규모를 아는 공범으로 묘사하지 않는다. 문제가 될 기록이 남았다는 사실을 어느 정도 알고 있으며, 죽은 자식을 지키려는 이기적인 애정에서 삭제를 재촉한다.
3. A 유족은 사건의 진실을 모르며 돈·법적 압박을 제시하지 않는다.
4. C에게서 새 메시지는 오지 않는다. 기존 A05의 삭제 요청을 최종 처리 화면에서 다시 보여준다.
5. 최종 화면 전에는 실제 원본을 삭제하거나 반출하지 않는다. 보존·삭제 후보는 처리안에 대한 표시일 뿐이다.
6. 비교·메모·고정·검색·특정 증거 조합은 P6 진행 조건이나 엔딩 판정에 쓰지 않는다.
7. 게임은 플레이어의 분류 결과를 좋은 엔딩·나쁜 엔딩·정답으로 표시하지 않는다.
8. 엔딩은 플레이어가 남긴 자료의 중요성이나 계약 위반 여부를 판정하지 않고, 두 유족 요청과 실제 처리 결과만 다시 보여준다.

## 3. P6 진행 순서

| 순서 | 화면 상태 | 플레이어 행동 | 결과 |
| --- | --- | --- | --- |
| 1 | P4 검토 완료 버튼을 눌러 P6 진입 | 없음 | B 의뢰에 `유족 추가 요청` 카드·알림 생성, 중앙 연락 오버레이 1회 표시 |
| 2 | B 연락 오버레이 | 내용을 확인하고 닫기 | B 연락 열람 완료 저장, 짧은 간격 뒤 A 연락 카드·알림 생성과 중앙 오버레이 1회 표시 |
| 3 | A 연락 오버레이 | 내용을 확인하고 닫기 | A 연락 열람 완료 저장, 최종 처리 화면을 한 번 자동 개방 |
| 4 | 자동 개방 뒤 또는 재실행 | 필요하면 상단 `최종 처리안 확인` 선택 | 최종 처리 화면 재개방 |
| 5 | 최종 처리 화면 | 현재 지정대로 처리 | 필요할 때만 계약 기본값 차이 경고, 결과 저장 뒤 엔딩 장면 표시 |

- 연락 도착과 알림은 효과 ID로 한 번만 실행한다.
- 두 연락은 최초 도착 때만 중앙 오버레이로 보여주고, 이후에는 각 의뢰의 업무 요청 카드에서 다시 열 수 있다.
- 완료까지 본 연락 오버레이는 재실행해도 자동으로 다시 띄우지 않는다. 표시 도중 종료했다면 해당 연락부터 이어서 보여준다.
- A 연락 오버레이를 닫으면 최종 처리 화면을 한 번 자동으로 연다. 이후 닫았거나 재실행한 경우에는 상단 `최종 처리안 확인`으로 다시 연다.
- 최종 처리 전에는 상단에서 최종 처리안을 다시 열 수 있다.
- 최종 처리 뒤에는 같은 세이브에서 결과를 바꿀 수 없다.

## 6. 연락 데이터와 진행 모델

### 확정 표시 구조 (2026-10-16 사용자 확정)

- `Request_B_FamilyFollowup`: 윤서하 의뢰, P6, F-B
- `Request_A_FamilyQuestion`: 서지훈 의뢰, B 연락 열람 뒤 공개, F-A
- `Job_B_FamilyFollowup`: P6 진입 뒤 B 요청 열람을 기다리고, 완료 시 A 요청을 공개한다.
- `Job_A_FamilyQuestion`: B 작업 완료 뒤 A 요청 열람을 기다리고, 완료 시 최종 처리안을 연다.
- 두 연락은 업무 요청 카드로 영구 보관하며 최초 수신 때만 같은 내용을 중앙 오버레이로 연속 표시한다.

### 구조 보강 원칙

- 두 요청을 모두 `availableFrom: P6`만으로 공개하지 않는다. A 요청은 B 요청 열람 완료 뒤에만 보여야 한다.
- 요청 공개 조건은 특정 에셋 이름을 화면 코드에 박지 않고 데이터 참조로 둔다.
- 요청 열람 이력과 작업 완료·알림은 기존 진행 저장 트랜잭션에 포함한다.
- 같은 연락이나 알림이 반복 평가·재실행으로 중복되지 않아야 한다.
- 양쪽 의뢰 어느 화면에 있든 현재 해야 할 연락 또는 최종 처리 버튼에 접근할 수 있어야 한다.

## 7. 최종 처리 데이터 모델

현재 `WorkStore`의 분류는 그대로 사용하되, 최종 처리 계산을 위한 편집 가능한 자료 묶음 데이터를 추가한다.

### 자료 묶음이 가져야 할 값

- 불변 묶음 ID
- 한국어·영어 표시 이름
- 계약 기본 처리: `보존` / `삭제`
- 처리 단위 목록: 원본 에셋 참조 + 필요한 경우 기기 참조
- 처리 단위별 포함 항목 수(기본 1)
- 화면 표시 순서
- 작가용 메모

### 계산 규칙

1. 같은 `RecordRef.Key`는 여러 UI 경로에 나타나도 한 번만 계산한다.
2. 실제로 서로 다른 기기·저장소에 존재하는 복사본은 서로 다른 처리 단위다.
3. 폴더는 처리 수량에 포함하지 않는다.
4. 유족 요청서·업무 알림·진행 요약은 저장 데이터 처리 대상이 아니므로 묶음과 수량 계산에서 제외한다.
5. 압축파일처럼 한 원본이 여러 항목을 포함하면 데이터의 포함 항목 수를 합산한다. A13의 `자료_2.zip`은 9다.
6. 수량은 화면 코드나 문자열에 상수로 넣지 않고 현재 데이터와 분류에서 계산한다.
7. 모든 접근 가능한 저장 데이터 처리 대상은 정확히 한 묶음에 속해야 하며, 누락·중복은 콘텐츠 검증 오류다.

| 미분류 | 자료 묶음의 계약 기본값 적용 |

- 업무 프로그램의 UI 기록에 남아 있는 구버전 분류 값은 계산에 사용하지 않는다.

## 10. 최종 처리 화면

서지훈 유족 문의 오버레이를 닫으면 이 화면을 한 번 자동으로 연다. 이후에는 상단 `최종 처리안 확인`으로 다시 연다.

### 10-1. 처리안 요약

> 최종 처리안

> 두 유족 요청과 현재 지정된 처리 결과를 확인합니다.

- `삭제 예정`: `{currentDeletedCount}`건
- `보존 예정`: `{currentKeptCount}`건

개별 기록, 내부 자료 묶음, 계약 기본 수량과 후보 수량을 한 화면에 반복하지 않는다. 플레이어가 최종 판단에 필요한 두 요청과 실제 처리 결과만 읽을 수 있게 한다.

- 명시적인 `보존 후보`는 보존하고 `삭제 후보`는 삭제한다.
- 미분류 자료만 묶음별 계약 기본값을 따른다.
- `자료 다시 검토`를 누르면 업무 화면으로 돌아가 분류를 바꿀 수 있다. 다시 열면 보존·삭제 예정 수량을 새로 계산한다.

### 10-2. 관련 요청

처리 수량 위에는 두 요청을 짧게 요약해 판단 없이 함께 보여준다.

**윤서하 유족 추가 요청**

> 개인 계정과 온라인 기록을 모두 정리해 달라는 요청

**서지훈 유족 문의**

> 서지훈이 그 장소에 있었던 이유를 알 수 있는 기록이 있는지 묻는 요청

- 정유진의 기존 삭제 요청은 조사 중 확인한 자료로 남기고, 최종 화면이 특정 자료와 자동 연결하거나 충돌을 선언하지 않는다.
- 두 요청의 상세 원문은 각 의뢰의 업무 요청 카드에서 다시 열 수 있다.

### 10-3. 처리 실행

버튼은 두 개만 둔다.

- `자료 다시 검토`
- `현재 지정대로 처리`


`현재 지정대로 처리`는 보존 후보와 삭제 후보를 그대로 실행하고, 미분류 자료만 계약 기본값으로 처리한다. 분류를 별도의 엔딩 선택으로 다시 묻지 않는다.

### 10-4. 계약 기본값 차이 경고

명시적인 분류가 계약 기본값과 다른 처리 단위가 하나 이상일 때만 확인 단계를 표시한다.

> 계약 기본값과 다른 지정이 있습니다.
>
> 계약 기본값과 다르게 지정된 자료 `{overrideCount}`건이 있습니다. 유족 요청 또는 계약 조건에 위배될 수 있으니 처리 전에 확인해 주세요.

- 보조 버튼은 `돌아가기`, 실행 버튼은 `확인하고 진행`이다.
- 프로그램은 계약 위반·보안 정책 위반·계정 정지·법적 결과를 확정하지 않는다.
- 기본값과 다른 지정이 없으면 이 경고를 생략하고 바로 처리한다.

### 10-5. 실행 연출

최종 실행 버튼을 누르면 다음 순서로 처리한다.

1. 현재 분류와 계약 기본값을 기준으로 대상 처리 단위와 보존·삭제 수량을 하나의 처리 스냅샷으로 계산한다.
2. 처리 스냅샷을 먼저 저장한다. 저장에 실패하면 실행하지 않고 확인 화면에 남는다.
3. 화면 입력을 잠그고 중앙에 `최종 처리 중`을 짧게 표시한다. 가짜 진행률이나 과장된 삭제 애니메이션은 사용하지 않는다.
4. 업무 UI를 덮는 엔딩 장면으로 전환한다.

- 정식 콘텐츠 에셋과 기존 작업 기록을 실제로 삭제하지 않는다.
- 실행 연출 도중 종료했더라도 재실행하면 저장된 스냅샷의 엔딩 장면으로 바로 복원한다.
- 엔딩 장면이 나타난 뒤에는 같은 세이브에서 처리안을 다시 열거나 결과를 바꿀 수 없다.

## 11. 엔딩 장면

업무 UI를 완전히 덮는 텍스트 중심의 별도 시퀀스로 표시한다. 계약상 삭제 대상의 보존 여부가 엔딩 분기이며, 프로그램의 즉석 판정이 아니라 처리 뒤 실제로 벌어진 결과를 보여준다.

### 11-1. 삭제 엔딩

계약상 삭제 대상을 하나도 보존하지 않았을 때 실행한다.

1. `처리 결과`와 보존·삭제 수량
2. 서지훈 유족의 질문
3. `확인할 수 있는 기록은 더 이상 남아 있지 않았다.`
4. 마지막 화면 `교차점`
5. `진실을 증명할 기록은 사라졌고, 사건은 기존 기록대로 남았다.`

### 11-2. 보존 엔딩

계약상 삭제 대상을 하나 이상 보존했을 때 실행한다. 남긴 자료의 중요성이나 진실 입증 가능성은 판정하지 않는다.

1. `처리 결과`와 보존·삭제 수량
2. `일부 기록은 보존 상태로 남았다.`
3. `며칠 뒤`
4. 내부 감사 결과 통지
5. 계약 범위를 벗어난 보존 이력 확인, 업무 접근 권한 회수, 고용 계약 종료
6. 마지막 화면 `교차점`
7. `일은 잃었지만, 기록은 남았다. 그 기록이 어디로 이어졌는지는 알 수 없다.`

- 보존·삭제 분류는 검토·법적 보존에도 쓰이는 정상 기능이며, 업무 프로그램은 실행 전에 위반을 확정하지 않는다.
- 최종 보존 이력이 감사 로그에 남고, 보존 엔딩의 책임은 시간이 지난 뒤 사람의 감사로 발생한다.
- 어느 엔딩에도 선택 버튼, 업무 화면 복귀, 좋은 엔딩·나쁜 엔딩 표기를 두지 않는다.

---

## 12. 엔딩 표시와 재생

- 검은 배경과 넓은 여백 위에서 문장·통지서를 한 장면씩 페이드한다.
- 삭제 엔딩은 질문과 빈 화면을 중심으로, 보존 엔딩은 프로그램과 다른 형식의 감사 통지서를 중심으로 구성한다.
- 첫 실행에서만 전체 시퀀스를 재생한다.
- 엔딩 도중 종료하거나 완료 뒤 재실행하면 해당 엔딩의 마지막 화면으로 바로 복원한다.
- 마지막 화면에는 제목, 결과 문장, 보존·삭제 수량, `의뢰 처리 완료`만 남긴다.

---

## 13. 저장과 재실행

- B 연락 도착·열람·오버레이 완료, A 연락 도착·열람·오버레이 완료, 최종 처리안 최초 자동 개방, 확정한 처리 스냅샷을 저장한다.
- 연락·알림·연락 오버레이는 각각 한 번만 완료 처리한다. 오버레이 도중 종료하면 완료되지 않은 연락부터 이어서 표시한다.
- 최종 처리안 최초 자동 개방은 한 번만 실행한다. 닫은 뒤나 재실행 뒤에는 상단 버튼으로 다시 연다.
- 최종 처리 전 재실행: 현재 단계에서 이어지고 상단에서 최종 처리안을 다시 열 수 있다.
- 최종 처리 뒤 재실행: 저장된 스냅샷과 같은 엔딩의 마지막 화면으로 복원하며 긴 시퀀스와 처리안을 다시 열지 않는다.
- 정식 콘텐츠 에셋이나 기존 작업 기록을 실제로 삭제하지 않는다. 결과는 저장된 처리 스냅샷과 완료 상태로 표현한다.
- 기존 P0~P6 진입 세이브를 읽을 수 있어야 한다.

---

## 14. 검증 기준

- B 연락을 보기 전 A 연락 0건
- B 연락 오버레이를 닫은 뒤 A 연락 1건·알림 1건·오버레이 1회
- A 연락 오버레이를 닫으면 최종 처리안 자동 개방 1회, 이후 상단 버튼으로 재열기 가능
- 반복 평가·재실행에도 연락·알림·완료한 오버레이·작업 완료 중복 없음
- 두 연락은 오버레이 완료 뒤에도 각 의뢰의 업무 요청 카드에서 재열람 가능
- 모든 처리 대상이 정확히 한 자료 묶음에 속하고 처리 단위 키 중복 0건
- 유족 요청서·업무 알림·진행 요약은 자료 묶음·화면·처리 수량에서 0건
- 분류 변경 뒤 최종 처리안을 다시 열면 보존·삭제 예정 수량과 계약 기본값 차이 수량 재계산
- `자료 다시 검토`로 업무 화면에 돌아가도 분류와 P6 진행 상태 유지
- 결과 수량은 처리 스냅샷 합계와 일치하며 모든 저장 데이터 처리 단위 합계와 같다.
- 계약 기본값과 다른 명시적 분류가 있을 때만 중립 경고 표시, 없으면 즉시 처리
- 경고 설명·수량과 엔딩 수량은 처리 스냅샷 결과에 일치
- 정유진 요청과 개별 자료 사이의 자동 연결·충돌 문구·충돌 수량 0건
- 업무 프로그램이 실행 전에 계약 위반·보안 정책 위반·계정 정지를 확정하는 문구 0건
- 계약상 삭제 대상 보존 여부에 따라 삭제·보존 엔딩이 정확히 분기
- 보존 엔딩은 내부 감사 뒤 접근 권한 회수·고용 계약 종료, 삭제 엔딩은 답할 기록 소실·사건 기록 유지 표시
- 엔딩 시퀀스는 최초 1회만 재생하고 재실행에서는 마지막 화면 복원
- 처리 스냅샷 저장 실패 시 결과로 넘어가지 않고 다시 실행 가능
- P0~P4에서는 P6 연락과 최종 처리안 접근 불가
- P6 진입 전 기존 검색·분류·메모·고정·비교·자료 접근 회귀 없음
- 콘텐츠 검증 오류·경고 0, 콘솔 오류·경고 0
- 실제 입력 검수는 수행하지 않고 사용자 확인 항목으로 남김

## 15. 사용자 결정 — 완료

- 업무 UI를 덮는 별도 엔딩 장면을 종착점으로 삼고 크레딧·타이틀 복귀 없이 `의뢰 처리 완료` 상태에 머문다.
- 플레이어가 게임 중 지정한 분류를 최종 처리에 그대로 사용하고 별도의 두 갈래 엔딩 선택을 다시 묻지 않는다.
- 재실행해도 확정한 처리 스냅샷의 엔딩을 복원하며 최종 처리안을 다시 열지 않는다.
