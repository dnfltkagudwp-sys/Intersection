## 0. 이 원고의 고정 규칙

### 0-1. P4 도달 상한

P4 자료를 모두 읽은 플레이어가 **자료만으로** 도달할 수 있는 최대치:

1. 윤서하의 휴대전화에 등록돼 있다가 사건 당일 연결 해제된 메일 계정이 있었다. 그 메일함에는 `@daylog_041`의 새 기기 로그인 알림과 `@smallroom_08`의 이용 제한 안내가 함께 들어 있다. 비밀번호 변경·게시물 삭제 안내도 같은 메일함에 있다. (B11)
2. 그 메일 계정의 복구 이메일 일부와 인증 전화번호 끝자리가, 윤서하 유족이 처음 맡긴 요청서의 개인 메일·휴대전화 정보와 각각 어긋나지 않는다. 둘 중 하나만으로는 누구 것인지 알 수 없다. (B12)
3. 윤서하의 삭제된 클라우드 백업 안 `Pictures/.work` 작업 폴더에 정유진·강나린·이름이 나오지 않는 한 사람의 사진이 각각 원본 사본 → 잘라낸 파일 → 편집 파일 → 내보낸 파일 → 캐시로 남아 있다. 같은 폴더에는 윤서하 자신의 사진도 같은 방식으로 다뤄져 있다. (B13)
4. 같은 작업 폴더와 메일함에는 끝까지 무엇인지 알 수 없는 오래된 파일 조각과 다른 계정 이름 조각이 있다. (B14, 선택)
5. 서지훈은 사건 당일 저녁, 메시지를 보내기 전에 기존 자료 9개를 압축해 올리고 링크를 만들고, 받는 사람이 비어 있는 메일에 그 링크를 붙여 둔 채 보내지 않았다. (A13 — P2부터 볼 수 있음)

P4 어디에도 다음은 없다: 윤서하가 쓴 문장, `범인`·`가해자`·`운영자` 같은 판정 문구, 계정 주인을 확정하는 시스템 표시, 피해 내용·수위의 묘사, 강나린이 입은 구체적 피해, 서지훈이 마지막에 찾은 자료, 폐상가 내부·사망 과정, 경찰 수사 범위, 윤서하 가족이 알던 범위.

### 0-2. 화면 문구 금지어

P2·P3 원고 0-2를 그대로 따르고, 이번 지시의 금지 표현을 더한다. 플레이어가 읽는 모든 문구(파일명, 경로, 미리보기, 메일 제목·본문·보낸 사람, 검색어, 설정 값, 요약·알림·상단 문구)에 다음을 쓰지 않는다.

- 결론형: `피해자`, `가해자`, `동일범`, `범인`, `정답`, `증거`, `유포`, `범죄`, `운영자`, `동일 인물`, `계정 주인`, `확정`, `자동 일치`, `추론 완료`
- 내부 표기: A/B/C/D/E 역할 호칭, 증거 ID(`B11`, `CROSS-2` 등), 원고 ID(`P4-B13-C2` 등), 상대 날짜(`D-182`), `P4`, 불변 ID, 자산 ID(`c-outfit-01` 등), 작가 메모
- 대본형 문장: 윤서하가 행동을 설명하는 문장. **P4에도 윤서하가 직접 쓴 문장은 하나도 없다.** 자료는 파일·경로·서비스 자동 메일·설정 값·레이어 이름뿐이다.

P3에서 금지했던 `temp`, `edit`, `export`, `cache`, 날짜 폴더명은 **P4에서 처음 등장하는 것이 의도**다(B13 구조). P0~P3 자료에는 계속 넣지 않는다.

### 0-3. 날짜·시각

- 모든 기록은 `time.dayOffset`/`hour`/`minute`/`sortKey`로 저장한다. 화면은 기존 규칙대로 `사망 182일 전`, 달력 날짜는 `caseDate`(임시 2025-11-14)에서 계산한다.
- **파일명·폴더명·본문에 달력 날짜를 글자로 박지 않는다.** `caseDate`가 임시라서 날짜 글자는 나중에 틀어진다. 날짜 폴더는 원본 경로에 토큰 `{folderDate:N}`으로 저장하고, **언어 비종속 설정 `GameConfig.folderDateFormat`(`yyMMdd`)**으로 변환한다(15절 결정 3). 변환 결과는 실제 저장 경로이므로 현지화 문자열이 아니며, 한국어·영어에서 같다. 폴더 탐색·파일 상세의 위치·검색·원본 열기가 모두 같은 변환 결과를 쓴다.
- 메일 본문에 시각을 쓰지 않는다(메일 목록·상세의 시각은 기록 시각에서 계산).
- 분 단위 시각과 정렬값은 이 원고가 확정한다. 파일명 숫자(`r0412`, `IMG_1157`)나 배열 순서로 시간을 추정하지 않는다.

### 0-4. 출처와 접근

| 묶음 | 기기 | 출처 | 접근 단계 | 여는 작업 |
| --- | --- | --- | --- | --- |
| B11·B12·B13·B14·일반 복구 53건 | 윤서하 의뢰 | `Recovered` | P4 | `Job_B_Recovery` (`unlocksSources: Recovered` — 현재 데이터 그대로) |
| A13 4건 + A 일반 5건 | 서지훈 의뢰 | `Cloud`(파일)·`Linked`(메일·설정) | **P2** | `Job_A_Inventory` (`unlocksSources: Cloud, Linked` — 현재 데이터 그대로) |

- 복구 자료의 기록 시각은 **원래 만들어지거나 받은 시각**이다. 삭제 시각은 기록마다 따로 두지 않는다. 언제 지워졌는지는 P3의 B16(사건 당일 20:14~20:22 백업 대상 축소·휴지통 비우기·계정 연결 해제)이 이미 보여준다.
- 복구 자료의 상태 표시(`integrityKey`)는 세 가지만 쓴다: `복구됨`, `일부만 복구됨`, `복구할 수 없음`(신규 키, 10절). 핵심 자료에만 다른 표시를 붙이지 않는다.
- A13은 A 클라우드 자료이므로 **P2부터 접근**한다. P4 전용으로 잠그지 않는다(12절 1번에서 기존 수량 변화 계산).

### 0-5. 원고 ID와 화면 기록 코드

- `P4-B11-1`, `P4-G-F3`, `A13-2` 같은 원고 ID는 이 문서와 작가 메모에서만 쓴다.
- 불변 ID는 에셋 생성 때 새로 발급한다. 화면의 `기록 ID`는 기존 규칙(`RecordCode`)대로 계산한다.
- 기존 원본은 새로 만들지 않고 실제 불변 ID로 재사용한다(6절).

### 0-6. 이미지

- **새로 생성하는 사진은 0장이다.** P4에 필요한 이미지는 전부 기존 원본(`c-outfit-01`, `d-group-01`, `e-partial-01`, 윤서하 갤러리 사진)을 실제로 크롭·가림·밝기 조정·압축해 파생한다(바이블 9-4 “원본 계보가 필요한 사진은 다시 생성하지 않는다”).
- 새 파생 이미지에는 글자가 없다. 글자가 있는 이미지는 D01-05 캡처 재렌더링 1장뿐이며, 이는 기존 P2 캡처 파이프라인의 정식 교체다(11절).

## 1. 메일 표현 — 추천안과 근거

### 1-1. 두 방안 비교

| 항목 | 방안 1: 기존 파일·브라우저·설정으로 표현 | 방안 2: 범용 메일 기록 + 읽기 전용 메일 화면 |
| --- | --- | --- |
| 표현 | 복구된 메일 캐시를 `Mail/Inbox/msg_000214.eml` 같은 파일로 두고 미리보기 문서에 머리글·본문을 적음 | `MailRecord`(보낸 사람·받는 사람·제목·본문 블록·첨부 줄·메일함·상태)를 기기 기록으로 추가하고, 목록(보낸 사람·제목·시각)과 상세(머리글 + 본문 + 첨부)를 읽기 전용으로 보여줌 |
| 장점 | 새 앱 없음 | 메일이 메일답게 보임. 목록에서 제목·보낸 사람으로 훑을 수 있음 |
| 단점 | 목록이 `msg_000214.eml` 같은 번호뿐이라 11건을 하나씩 열어야 함. B13 30건과 같은 파일 앱에 몰려 **P4 자료가 한 앱에 몰리는 문제**를 키움. A13 미발송 메일을 `.eml` 파일로 두면 “보내지 않았다”가 파일 속성으로만 남아 부자연스러움 | 코드 추가(기록 종류 1개, 앱 1개, 목록·상세는 기존 범용 기록 화면 재사용) |
| A13 | 임시 보관 메일을 파일로 둠 — 부자연스러움 | 서지훈 메일함의 `임시 보관함`에 받는 사람이 빈 메일로 자연스럽게 남음 |
| 수량 | — | 윤서하 11건 + 서지훈 6건 = **17건**이 공용 구조를 씀 |

### 1-2. 추천: 방안 2 (작은 읽기 전용 메일 앱)

- 공용 구조가 실제로 이득이다. B11 4건·B12 2건·B14 1건·일반 4건(윤서하)과 A13 2건·일반 4건(서지훈)이 같은 구조를 쓴다. 파일로 합치면 메일 11건이 복구 파일 34건과 한 화면에 섞인다.
- 만들지 않는 것: 쓰기·답장·전달·검색창·폴더 이동·첨부 열기·외부 링크 열기. 메일함은 기록의 `메일함` 값으로 목록에 섹션 머리만 나눈다(`받은편지함`, `임시 보관함`).
- 코드 범위(구현 단계 참고, 15절 결정 1 승인 후):
  - `RecordKind` 끝에 `Mail`, `AppKind` 끝에 `Mail`을 추가한다(정수 순서 유지).
  - `MailRecord : DeviceRecord`의 필드:
    - `mailboxKey`(`mail.box.inbox`/`mail.box.drafts`), `fromName`, `toKey` 또는 `toText`
    - `subject`, `body`(`FileTextBlock` 목록 재사용), `attachments`(줄 목록)
    - `statusKey`(초안이면 `mail.status.unsent`)
  - 화면:
    - 목록·상세는 브라우저·설정과 같은 범용 기록 경로를 쓴다.
    - 앱 등록 정보(`Apps.asset`)에 한 줄을 추가한다.
    - 연동 결과 요약에 `메일` 분류를 추가한다.
  - 검색: 제목·보낸 사람 표시명·본문 각 줄·첨부 줄을 현재 언어 값으로 인덱싱한다.
  - 열람 판정: 메일 상세를 연 것(`MarkViewed`).
  - **새 기록 종류가 기존 기록과 같은 대우를 받도록 함께 바꿀 곳 (구현 범위 전체):**
    - `ContentDatabase` 목록과 자동 동기화(`ContentDatabaseSync`)
    - `RecordRef`(종류 이름 저장), `RecordResolver`(원본 찾기·누락·중복), `RecordAccess`(접근 단계)
    - 앱 목록 수량, 연동·복구 결과 요약 수량
    - 전역 검색(`GlobalSearch` 문서·결과 그룹·결과 열기)
    - 원본 열기(작업함·고정 목록·검색 결과에서 메일 상세로 이동)
    - 작업함·고정·분류(보존/삭제)·작업메모·우측 패널 상세
    - 비교 화면(메일을 읽기 전용 상세로 표시)
    - 삭제 대기 계산(`DeletionQueue.Compute`)
    - 기기별 탐색 상태 복원(의뢰 전환 시 메일 앱의 목록·상세 위치)
    - 검증 도구의 누락·중복 ID·접근 불가·시각·현지화 검사
    - 기존 세이브 호환(새 종류 이름이 없는 예전 세이브는 그대로 로드, 알 수 없는 종류는 누락 상태로 보관하는 기존 규칙 유지)
- 빈 상태:
  - 서지훈 메일 앱은 P0·P1에 비어 있다(메일은 연동 계정 자료라 P2부터).
  - 윤서하 메일 앱은 P1~P3에 비어 있다. 메일 계정은 사건 당일 연결 해제됐다(B16-3).
  - 지금도 윤서하 파일 앱이 P1·P2에 비어 있으므로 빈 앱은 새 문제가 아니다. 문구는 `메일 없음`(신규 키).

### 7-2. 한 번만 완료되는 구조 (기존 데이터 방식, 코드 최소)

현재 `Job_B_Recovery`는 `completedExternally 1`, 완료 효과 = `RaiseStage P4` + `Notify notify.recoveryDone`이다. 다음처럼 바꾼다(15절 결정 7).

| 필드 | 현재 | 변경 |
| --- | --- | --- |
| `completionConditions` | 없음 | `JobCompleted(Job_B_Inventory)` 1개 — 시작 시점에 이미 참이므로 “시작하면 곧 완료”를 데이터로 표현 |
| `autoCompleteWhenReady` | 0 | 1 |
| `completedExternally` | 1 | 0 (자동 완료 작업. P3 마감의 B 인벤토리와 같은 정리) |
| `onComplete` | RaiseStage P4 + Notify | + `SyncSummary`(신규 효과 ID, `templateKey notify.recoveryDone`, `caseToken` 윤서하 의뢰, 요약 문구 키 3개 — 결정 8) |

- **한 번만:**
  1. 시작 클릭은 기존 `Progression.Start` 트랜잭션으로 작업을 `Running`으로 저장한다.
  2. 바로 이어서 `AfterProgressChange → Evaluate → AutoComplete`가 별도 트랜잭션으로 완료·P4·알림·요약을 저장한다.
  3. 효과 ID 중복 방지와 “완료된 작업은 다시 완료하지 않음”이 반복을 막는다.
- **중간 종료:** 1과 2 사이에 꺼지면 다음 실행의 `InitProgress → Evaluate`가 완료시킨다. 알림·요약은 한 번만 생긴다. 요약을 보기 전에 꺼지면 재실행 때 요약이 다시 표시된다(기존 `seen`).
- **화면 순서 (현재 코드와의 차이):**
  - 지금 `StartJob`은 `Progression.Start` 직후 `AfterProgressChange()`를 부른다. 자동 완료와 요약 자동 표시까지 그 자리에서 진행된다.
  - 데이터만 바꾸면 처리 화면이 보이기 전에 요약이 열린다. 그래서 다음 순서를 구현한다(결정 7).
  1. 클릭 즉시 작업 시작·자동 완료·P4·알림·요약 기록을 지금처럼 저장한다(데이터는 기다리지 않음).
  2. 시작한 작업의 데이터에 처리 연출 키가 있으면 중앙에 복구 처리 오버레이를 연다. 신규 범용 필드 `startPresentationKey`(문구 키, 예 `recovery.processing`)와 `startPresentationSeconds`(예 1.0)를 쓰고, **특정 작업 ID는 비교하지 않는다.**
  3. 오버레이가 열려 있는 동안 요약 자동 표시를 보류한다. 비교 중 요약을 보류하는 기존 규칙과 같은 방식이다.
  4. 약 1초 뒤, 또는 클릭·Enter로 건너뛰면 오버레이를 닫고 보류 중인 복구 요약을 연다.
  5. 연출 도중 종료하면 재실행 때 연출은 생략한다(오버레이 상태는 저장하지 않음). 확인하지 않은 요약만 기존 `seen` 규칙대로 표시한다.
- **디버그 없이 정상 흐름으로 진입:** 플레이어가 상단 버튼을 누르는 것뿐이다. 진행 검수 창의 `완료(효과)`는 더 이상 필요 없다.
- **검증 도구:**
  - 자동 완료를 켜면 그 단계(P4)에 이 작업이 여는 출처(`Recovered`)의 정식 기록이 있어야 한다. P4 기록 53건으로 충족된다.
  - P3 마감 때 보강한 도달 가능 단계 계산이 자동 완료 작업을 완료 경로로 인정하므로, 8절 신규 작업의 P4 자료 조건이 통과한다.
